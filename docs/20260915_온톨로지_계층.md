# IS_A 계층(온톨로지) 도입 (2026-09-15, 팀 합의)

## 왜
전공↔직무 공통 Skill이 8개에서 멈춘 원인은 어휘가 아니라 **추상화 수준 차이**: 직무는 도구명(Java, React, Kubernetes, Oracle),
전공은 학문명(Algorithm, Database, Statistics). 글자가 같아야 잇는 flat 어휘집으로는 "Oracle ≈ Database"를 모른다.
`vocab.PARENT`에 "자식 IS_A 부모"를 한 단계만 적고, 매칭 때 **직무 요구를 위로 올려** 비교한다.

## 규칙
1. 한 단계만 (Programming → CS → IT 로 두 단계 올리면 변별력 0)
2. 상위 개념도 과목명에서 근거를 댈 수 있는 단어만 (Database ○, IT ×)
3. 추론은 위로만 — 직무 Oracle → "Database 계열 요구"(참). 전공 Database → "Oracle 가르침"(환각) 금지

## 실측 (같은 graph.json, LLM 재호출 없음)
- 정확 공통 Skill 8개 그대로 + **IS_A 한 홉으로 이어지는 직무 역량 23개** (AWS, Docker, Kubernetes, Git, React, Spring Boot, LLM, RAG …)
- "데이터 분석" 입력 → AI (AX) 직무: 요구 10개 중 **7개 커버 (정확 1 · 계열 6)**. 계층 전에는 Consulting 2개 중 1개
- Neo4j로 쓰면 `(need)-[:IS_A*0..1]->(have)` — 0홉=정확, 1홉=계열. 이 가변 길이 경로가 "DB가 아니라 Knowledge Graph"인 이유 (발표 4·5장)

## 남은 것
- raw 캐시는 `Programming`이 어휘에 없던 시점의 출력 → 컴공 등 16개 전공에 '프로그래밍' 과목이 있어도 아직 안 붙음. 재추출 필요

- D: 직무 추천 시 `career_type == "신입"` 우선 (취준생 대상인데 경력 공고가 1위로 나오는 경우 있음)

## 매칭 동결 (2026-09-15 저녁)
- 전공 점수: **IDF 가중 커버리지** — `idf(s) = log(전공 수 / s를 기르는 전공 수)`. 흔한 역량(Data Analysis, 42/63)은 0.41, 드문 역량(Signal Processing, 3/63)은 3.04.
  사용자 태그의 무게 중 전공이 채운 무게의 비율. 계열 일치 0.5. 동점은 근거 과목 수.
- 직무 점수: 집합 코사인 + 계열 0.5 (그대로). 역량 2개 미만 직무는 그래프에서 제외.
- **평가셋 `evals/cases.json` 10건**을 `check.py`가 돌린다 (기대 전공 top-3 / 기대 직무명 조각 top-2). 현재 9/10 — #8 기계공학은 어휘 공백(2단계).
  이후 매칭 변경은 통과율로 판단한다. 시연 답변 3세트는 여기서 고른다.

## 두 번째 관계: 성향 → 역량 (SUGGESTS) — 인터뷰 모드 (2026-09-15 밤, 팀 결정)
- 팀원의 `user_analysis/`(자기소개 → 7개 영역 프로필, 성향 30개)를 **입력 단계**로 붙임. 어댑터 `interview.py` 하나로, 원본 파일은 수정 없음.
- 쓰는 영역은 `interest`(텍스트 → 태거)와 `strength`(성향 → `vocab.TRAIT_TO_SKILL` 7개 → 태그) 둘. 나머지 5개는 매칭 근거가 없어 호출하지 않음.
- IS_A(분류, 항상 참)와 달리 이건 **연관**(경향). 그래프로는 `(:Trait)-[:SUGGESTS]->(:Skill)` — 다른 노드·다른 엣지. 근거(과목명)가 없으므로
  태그 신뢰 가중치 0.5(`graph_store.find_majors_by_skills(tag_weights=)`), 화면에 "성향에서 추정"으로 구분 표시.
- 재현성: 질문은 LLM 생성이 아니라 `PROFILE_AREAS` 고정 질문, 영역당 1회. LLM 최대 3회 + 태거 1회.
- 페르소나 확정: 진로 탐색 중인 **고등학생**. 3질문 모드 문구도 그 톤으로. 실행 `python app.py --interview`.
- 평가셋 `evals/interview_cases.json` 2건 (풍부한 자기소개 → 1회 / 빈약 → 3회) 통과.

## 세 번째 관계: 성향 → 소프트 스킬 ← 직무 (2026-09-16 새벽) + 관심사 사전 직행
- `interest.domains/activities` 는 텍스트로 태거에 넣지 않고 **`canonicalize()` 로 먼저 태그화** (LLM 0, 근거 = `interest.evidence`).
  사전에 없는 표현만 자기소개 원문과 함께 태거로. 같은 내용을 LLM 이 두 번 읽던 낭비 제거.
- 직무의 `soft_skills`(추출돼 있었지만 미사용, 84건 중 35건 유효) → `vocab.SOFT_CANON` 10개로 정규화해 Job 노드 `soft`.
  학생 강점 성향 → `vocab.TRAIT_TO_SOFT`(17개) → 대조. 그래프: `(:Trait)-[:MATCHES]->(:SoftSkill)<-[:WANTS]-(:Job)` — 전공을 거치지 않는 세 번째 관계.
- **점수에 더하지 않는다.** 빈 `soft` 가 "요구 없음" 인지 "추출이 놓침" 인지 구분이 안 되므로(84건 중 49건 없음) 알 수 없음 = 0 으로 두고,
  기술 점수가 **인접 0.01 안**인 동점 그룹에서만 적합 개수로 재정렬 (`graph_store._reorder_ties`). 반올림 버킷은 경계 쌍(0.4763/0.4714)이 갈려서 폐기.
- 약점(direction=weakness)은 쓰지 않는다 (user_analysis 규칙 14). 카드에는 데이터가 있는 직무만 "요구 태도: 협업 ✓ · 문제해결 ✓" — ✗ 표시 없음.
- 성향 30개 중 쓰이는 것: 기술 역량 7 + 소프트 17 = 팀원 모듈의 어휘 대부분이 화면에 나타남.
