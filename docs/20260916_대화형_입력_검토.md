# 검토: 사용자 입력을 "LLM과 대화하듯" 바꿀 수 있나 (2026-09-16)

> 팀원 제안 "사용자 입력을 LLM과 대화하는 것처럼" 에 대한 가능성 검토. 결정은 팀이 한다 — 맨 끝 체크리스트.

## 결론 먼저

**가능하다. 재료의 80% 는 이미 저장소에 있다.** 단, 선 하나를 지켜야 한다:

> **대화는 입력층이다. 판정(전공·직무·과목)은 지금처럼 도구(`graph_store`)가 한다.**

이 선을 넘어 LLM 이 대화 중에 전공이나 직무를 직접 말하기 시작하면, 발표 5장의 차별점(전수 순위 · 커버리지 갭 · 출처 꼬리표 · 재현성)이 전부 사라지고 "그냥 챗봇" 이 된다.

## 1. 지금 구조와 바뀌는 자리

```
[지금 · 인터뷰 모드]
자기소개 → analyze_introduction (LLM 1)
  → 부족한 영역만 고정 질문 (PROFILE_AREAS main_question, 최대 2)  → analyze_area_answer (LLM 1/회)
  → interest → 사전 직행 태그 / strength → TRAIT_TO_SKILL·TRAIT_TO_SOFT
  → app.run() → graph_store (LLM 0) → 카드 → explain (LLM 1)

[제안 · 대화형]
자기소개 → analyze_introduction (LLM 1)
  → 부족한 영역이 있는 동안 (최대 3턴):
        generate_next_question (LLM 1)  ← 고정 문구 대신 LLM 이 만든 질문   ★ 바뀌는 자리
        → 학생 답 → analyze_area_answer (LLM 1)
  → 이후는 지금과 완전히 동일
```

바뀌는 건 **질문 한 줄을 누가 만드느냐** 뿐이다. `interview.py` 가 `run()` 에 넘기는 계약(`answers / interest_tags / trait_tags / soft_traits`)은 그대로라 `graph_store.py`·`app.py`·평가셋 구조가 안 깨진다.

## 2. 이미 있는 재료

| 파일 | 있는 것 | 상태 |
|---|---|---|
| `user_analysis/question_agent.py` | `generate_next_question(missing_areas, conversation) → QuestionResult(area, question)` — 부족한 영역을 보고 다음 질문을 LLM 이 생성 | 팀원 작성, **우리 파이프라인에서는 아직 안 씀** |
| `user_analysis/main.py` | `while not is_profile_complete(profile)` 루프, 영역당 질문 2회 제한, 대화 기록 문자열화 | 대화 루프의 뼈대 |
| `user_analysis/prompts.py` (9/16 갱신) | "행동 근거가 있을 때만 성향 추출" 규칙, `mapped_traits` | 대화가 길어질 때 지어내기를 막는 장치 |
| `interview.py` | 자기소개 → 부족 영역 질문 → `run()` 어댑터 (`ask`/`say` 주입 가능) | 고정 질문을 생성 질문으로 바꾸면 끝 |
| `webapp.py` | 세션 상태 dict, `/api/submit`, SSE 스트리밍 | 채팅 UI 로 확장할 토대 (턴마다 `/api/turn` 하나 추가) |

## 3. 최소 구현안 (반나절, `app.py` 무수정)

1. `interview.py` 의 고정 질문 한 줄 → `generate_next_question(missing_areas, 대화기록)` 호출로 교체
2. 종료 규칙을 코드로: `is_profile_complete` **또는** 턴 3회 **또는** 영역당 2회 — 셋 중 하나면 멈춘다
3. `question_agent` 의 `temperature=0.3` → `0` (평가셋 재현성)
4. `webapp.py` 에 턴 단위 엔드포인트 1개 (`/api/turn`: 답 하나 받고 다음 질문 또는 결과 id 반환)
5. `evals/interview_cases.json` 의 대본을 "영역별 답변 사전" 으로 바꿈 — 어떤 질문이 와도 그 영역의 답을 돌려주게 (질문 문구가 매번 달라도 자동 검증이 돈다)

## 4. 검토해야 할 쟁점

| 쟁점 | 내용 | 대응 |
|---|---|---|
| **호출 수** | 지금 인터뷰 3~5회. 대화형은 턴당 2회(질문 생성 + 분석) → **최대 1 + 3×2 + 2 = 9회** | 턴 상한 3. 자기소개가 충분하면 0턴(=지금과 같은 3회). 발표 3장 호출 수 표에 한 줄 추가 |
| **언제 멈추나** | LLM 은 스스로 안 멈춘다. 규칙이 없으면 계속 묻는다 | 3절 2번. 종료 판단은 LLM 이 아니라 코드가 |
| **평가셋** | 질문이 매번 달라지면 대본 주입이 못 따라간다 | 3절 5번 + temperature 0. 검증 대상은 "최종 태그·전공·직무" 로 유지 |
| **지어내기** | 대화가 길수록 근거 없는 성향이 붙을 위험. 이 프로젝트에서 "개수를 시키면 지어낸다" 4회 관측 | 9/16 프롬프트의 "행동 근거 있을 때만" 규칙 유지, `TRAIT_MIN_CONFIDENCE 0.6` 유지, 질문 생성 프롬프트에 "한 번에 한 가지만 묻는다" |
| **일정** | 발표 금요일. `app.py` 는 별도 작업 중 | `interview.py`·`webapp.py`·`question_agent.py` 만 건드리면 충돌 없음 |

## 5. 하지 말아야 할 것

- 대화 안에서 LLM 이 전공·직무를 **직접 추천**하게 하는 것 → 챗봇과 같아짐
- 태그를 LLM 이 자유롭게 정하게 하는 것 → 통제 어휘 밖 태그는 그래프와 안 이어진다 (지금처럼 `TAGS` 목록 안에서만)
- 턴 상한 없이 "충분할 때까지" → 비용·지어내기 둘 다 커진다

## 6. 별개 기능: 결과에 대해 되묻기 ("왜 이 전공이야?")

"LLM 과 대화" 를 **출력 쪽**으로 해석하면 이건 다른 기능이다. 가능은 하다: `build_explain_prompt(r)` 의 근거(카드 내용)만 컨텍스트로 주고 학생 질문에 답하되 **"근거에 없으면 모른다고 답한다"** 를 규칙으로 — 질문당 LLM 1회. GraphRAG 의 축소판이라 확장 과제로 말하기 좋다. 발표 전 구현은 권하지 않는다.

## 7. 추천

- **목요일 오전**: 3절 1~3번(고정 질문 → 생성 질문, 종료 규칙, temperature 0) + 5번(평가셋 대본 방식) → 리허설
- **웹 채팅 UI**(3절 4번)는 시간이 남으면
- 자유 대화·결과 되묻기는 **확장 과제 슬라이드**
- 발표 문장: "대화는 LLM 이, 판정은 그래프가 — 그래서 대화형으로 바꿔도 전수 순위·갭·출처는 그대로다"
